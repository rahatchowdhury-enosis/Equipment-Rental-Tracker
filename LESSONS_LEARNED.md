## Domain: Infrastructure
### Component: Project Scaffold & Auth
- **Issue:** [TASK-1] - Laravel Project Scaffold, Breeze Auth, Xdebug Config
- **Lesson:** Planned MySQL/MariaDB stack was switched to PostgreSQL + Laravel 12 mid-implementation — every `laravel/framework ^11.x` release available at the time carried unfixed security advisories, and local MySQL credentials couldn't be recovered, while a working local Postgres instance existed. Also: a stock Laravel config file (`config/database.php`) referencing a PHP-8.5-deprecated PDO constant silently broke session cookies by echoing a deprecation notice into the response body before headers were sent — status codes alone (200/302) did not reveal this; only inspecting raw response headers for a missing `Set-Cookie` surfaced it.
- **Action:** When bootstrapping a new Laravel app, run `composer audit` immediately after `create-project` and before committing to a framework minor version. When debugging "requests succeed but auth state doesn't persist," check for output printed before headers (deprecation notices, stray `echo`) rather than assuming the session driver is misconfigured. TASK-9 (which plans to add real content to `app/helpers.php`) and TASK-17 (README) should assume PostgreSQL, not MySQL — `REQUIREMENTS.md` and `designs/TASK-1.md`/`TASK-17.md` were updated accordingly. Note for whichever future task adds the deliberate raw-PDO query (REQUIREMENTS §4): `phpunit.xml` currently runs the test suite against in-memory SQLite, not Postgres, so a raw-SQL query written for Postgres syntax may pass tests without ever running against the real target DB — consider a dedicated Postgres-backed test for that one query.

- **Issue:** [TASK-2] - Database Migrations for equipment, staff, rentals
- **Lesson:** Unlike MySQL, Postgres does not auto-index foreign-key columns, so `foreignId()->constrained()` alone leaves `rentals.equipment_id`/`staff_id` unindexed — chaining `->index()` directly onto a `foreignId()->constrained()->cascadeOnDelete()` call also fails on Postgres (`SQLSTATE[42710]: constraint "1" already exists`, an anonymous-name collision in Laravel's fluent chain); a separate `$table->index('column')` statement after the column definitions is required instead.
- **Action:** On Postgres, always add explicit `$table->index()` calls for FK columns that will be queried or joined on (any table a later task will filter/paginate by that FK) — never assume `constrained()` provides one, and never chain `->index()` onto a `constrained()->cascadeOnDelete()` foreignId definition.

## Domain: Infrastructure
### Component: Eloquent Models — Equipment, Staff, Rental
- **Issue:** [TASK-4] - Eloquent Models with relationships, enum casts, and clone-based catalog duplication
- **Lesson:** A raw PHP `clone $original` on an Eloquent model copies full model state, including `exists` and the primary key attribute — saving it as-is does not throw, it silently `UPDATE`s the original row. Nulling `id` alone is also insufficient on Postgres: an explicit `NULL` still gets bound into the INSERT and Postgres rejects it for a `bigserial` PK (unlike SQLite, which auto-assigns a rowid). The correct pattern is `$copy->exists = false; $copy->offsetUnset('id');` before reassigning the unique field and saving — `replicate()` already does this correctly and is the framework-idiomatic path.
- **Action:** Prefer `replicate()` over raw `clone` for persisting model duplicates; if raw `clone` is ever used for demonstration or a real feature, always pair it with `exists = false` + unsetting the PK attribute, and test that path against Postgres semantics (SQLite's `phpunit.xml` suite will not catch the NULL-PK rejection — noted from TASK-1's lesson on the same SQLite/Postgres test-parity gap).

## Domain: Infrastructure
### Component: Factories & Seeders — Demo Data
- **Issue:** [TASK-5] - Factories & Seeders for equipment/staff/rental demo data
- **Lesson:** A seeder that creates `Rental` rows without also updating the parent `Equipment.status` produces a self-contradicting dataset (item shows Available while a rental has it checked out) — code review caught this as a BLOCKER because nothing in the schema enforces that invariant; it only shows up as a downstream app bug (availability list, checkout flow, overdue report). Separately, a bare `User::firstOrCreate()` (as opposed to `User::factory()->create()`) skips factory-only fields like `password`/`remember_token`, so it throws a NOT NULL violation the moment idempotency is added naively.
- **Action:** Whenever a seeder/factory creates a row that mirrors state onto a related row (rental ↔ equipment status, order ↔ inventory count, etc.), update both sides in the same seeder pass and add a test asserting the *relationship* is consistent, not just that row counts match. When making a `User`-derived seed idempotent, guard with an existence check before `User::factory()->create()` rather than swapping in a bare `firstOrCreate` on the base model.

## Domain: Infrastructure
### Component: OOP Foundations — RentableInterface, BaseService, Loggable, DTO
- **Issue:** [TASK-6] - OOP Foundations — RentableInterface, BaseService, Loggable Trait, DTO + LSB Demo
- **Lesson:** A trait method test (`Log::info(static::class . ...)`) written against an anonymous class can pass even if the `static::class` prefix logic is broken or removed, because the assertion only checked `str_contains($message, '...')` rather than the exact expected string — code review caught it as a WARN since the late-static-binding behavior the trait exists to demonstrate was effectively untested.
- **Action:** When a test's whole point is to prove a class-name-derived value (LSB, `static::class`, `self::class` in a trait), assert full string equality against a named fixture class, not `str_contains` against an anonymous class — a loose substring match on a subject's own literal text can pass regardless of whether the mechanism under test actually ran.

## Domain: Infrastructure
### Component: Form Requests — StoreEquipmentRequest, StoreStaffRequest
- **Issue:** [TASK-7] - Form Requests — StoreEquipmentRequest, StoreStaffRequest
- **Lesson:** `Illuminate\Http\Request::__get()` resolves request *input* before falling back to the route parameter (`Arr::get($this->all(), $key, fn () => $this->route($key))`), so `Rule::unique(...)->ignore($this->equipment)` lets an attacker override which record gets ignored just by adding an `equipment`/`staff` field to the request body — the fix is `->ignore($this->route('equipment'))`, which only ever reads route-model-binding. A unit test built with `Validator::make($data, $rules)` alone cannot catch this: the payload only reaches the validator, never the `FormRequest` instance, so `$this->equipment` and `$this->route('equipment')` are indistinguishable unless a test actually merges spoofed input onto the request object itself (`$request->merge([...])`) before calling `rules()`.
- **Action:** Any `FormRequest` using `->ignore($this->someRouteParam)` for an update-safe unique rule must use `$this->route('someRouteParam')`, never the magic property/array-access form. When unit-testing that guard without a real HTTP route (as here, ahead of TASK-8/9's controllers), assert against a request with spoofed conflicting input merged in, not just a route-resolver stub — a stub alone proves the ignore *works*, not that it resists request-input shadowing.

## Domain: Language Fundamentals
### Component: helpers.php, Raw Array Pass, Raw Superglobal Dump
- **Issue:** [TASK-9] - helpers.php, Raw Array Pass, Raw Superglobal Dump
- **Lesson:** `DateInterval::format('%a')` is always unsigned regardless of argument order, so a naive `$from->diff($to)->format('%a')` helper silently returns the same positive value whether `$from` is before or after `$to` — a real bug for any "days late"/"days remaining" consumer (TASK-16's overdue report) that needs sign to distinguish overdue from early. It also truncates non-midnight timestamps toward zero (`23:00 → next day 01:00` reports `0` days), undercounting a calendar-day boundary crossing. Separately, TASK-8's already-documented factory-name-collision flakiness (small `randomElement` pool for `name`) recurred here in a new test that asserted on equipment `name` instead of `serial_no`/pinned values — the lesson had been written down but not checked against when writing the new test.
- **Action:** Any day-count helper built on `DateInterval` must normalize both operands to date-only (strip time-of-day) before diffing and explicitly return a signed result (`$from > $to ? -$days : $days`) rather than trusting `%a`'s magnitude. Also: raw superglobal/request dumps gated behind `app()->environment('local')` still need field-level redaction (`Arr::except($_GET/$_POST, ['_token','password','password_confirmation'])`) since "local only" does not mean "safe to log secrets" — local logs get shared/committed too. Before writing a new Feature test on this model, grep this file for prior lessons about the same model/factory (the `name`-collision one exists since TASK-8) instead of re-discovering it via a flaky CI run.

## Domain: Web CRUD
### Component: StaffController — CRUD, GuestStaff Anonymous Class
- **Issue:** [TASK-10] - Staff CRUD — Controller, Views, GuestStaff Anonymous Class
- **Lesson:** PHP enforces covariant return types even across an anonymous `extends` subclass: `Staff::activeRentals(): HasMany` cannot be overridden with a method returning a plain `Collection` — it fatals at class-declaration time (`Declaration ... must be compatible`), not at call time, so the failure surfaces the instant the anonymous class is instantiated, unrelated to whether the overridden method is ever invoked directly vs. via magic property access. The correct null-object pattern is to keep the real relation type and force an empty result (`$this->rentals()->whereRaw('0 = 1')`), not to swap in an unrelated return type. Separately, `auth()->id()` returns `null` when unauthenticated, and `Staff::where('user_id', null)` compiles to `WHERE user_id IS NULL` — since the factory default is `user_id => null`, this silently matched any unlinked staff row as "current staff" instead of falling through to the Guest object; only caught because a test seeded an unlinked staff row and called the guest-resolver unauthenticated. Also: Eloquent's `exists` is a public *property* (`$model->exists`), not a method — defining a method named `exists()` on a subclass doesn't override anything, and calling `->exists()` on an unrelated real model forwards through `Model::__call` to a fresh, unconstrained `Builder::exists()` (answers "does this table have any row at all", not "is this instance persisted").
- **Action:** Any null-object/guest subclass overriding an Eloquent relation method must preserve the parent's declared return type and force emptiness inside a real relation query, never swap in a plain `Collection`. Any `Model::where('col', auth()->id())` guard must short-circuit on a `null` id explicitly (`$id = auth()->id(); $id ? Model::where(...) : null`) rather than trusting the query to naturally exclude unauthenticated callers — nullable FK columns turn "no id" into a real, matchable `IS NULL` clause. Never define a method literally named `exists()` on an Eloquent model subclass to represent persistence state; rely on the inherited `$exists` property instead. Authorization was again deliberately left at `auth`-only, consistent with TASK-8's precedent — no `Policy` convention exists yet in this app, and this ticket's AC didn't call for one; flagged as an explicit deferred WARN in code review rather than silently skipped.

## Domain: Web CRUD
### Component: EquipmentController — CRUD, Photo Upload, Duplicate
- **Issue:** [TASK-8] - Equipment CRUD — Controller, Views, Photo Upload
- **Lesson:** Storing a photo path on `update()`/`destroy()` without deleting the previously stored file orphans files in `storage/app/public/equipment`; duplicating via `Equipment::duplicateWithSerial()` (which uses `replicate()`) also copies the source's `photo` path and `status` verbatim, so two DB rows end up pointing at one shared file and a duplicated catalog entry can inherit a `checked_out` status with no rental attached. Also: `factory()`-generated names come from a small fixed pool (`fake()->randomElement([...])`), so two independently-created rows can collide on `name` — a test asserting on equipment `name` to distinguish two rows is flaky; assert on `serial_no` (factory-guaranteed unique) instead.
- **Action:** Any controller action that replaces or deletes a model's stored file must explicitly `Storage::disk(...)->delete()` the old path first — Eloquent `update()`/`delete()` never touches the filesystem on its own. Any duplication path that reuses `replicate()`/`clone` must explicitly null out or reset fields that shouldn't be shared across rows (file paths, status flags tied to a relationship) rather than assuming the copy should mirror the source. Authorization was deliberately left at `auth`-only for this task — the app has no `Role`↔`User` linkage or `Policy` convention anywhere yet, so scoping equipment mutation to a role belongs to whichever future task introduces real RBAC, not a CRUD-scaffolding task.
